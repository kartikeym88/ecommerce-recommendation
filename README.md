# ecommerce-recommendation

A recommendation engine for e-commerce platforms. It takes raw user activity (page views, clicks, purchases, ratings) and produces a ranked list of products the user is likely to want next.

The system combines three scoring strategies and picks the right one depending on how much data it has about a given user:

- **Collaborative filtering** for users with enough interaction history. It builds an item-item similarity matrix from the sparse user-item matrix using cosine similarity, then scores unseen items based on what similar items the user already engaged with.
- **Content-based filtering** for users who have some history but not enough for CF to be reliable. It uses TF-IDF vectors built from product metadata (category, subcategory, brand, tags, description) and computes a user profile as a weighted average of the items they interacted with.
- **Popularity fallback** for brand-new users with zero history. It just ranks items by global interaction volume.

The hybrid orchestrator (`HybridRecommender`) decides which strategy to use based on a configurable cold-start threshold, then blends the normalized scores with tunable weights (default: 0.5 CF, 0.3 Content, 0.2 Popularity for full-history users).

## How it works

### Data pipeline

Raw interaction logs go through three stages:

1. **Validation and cleaning** (`DataProcessor`): drops rows with missing user/product IDs, removes duplicate interaction IDs, clips ratings to [1, 5], and filters out any future-dated timestamps.

2. **Implicit strength calculation**: each event type gets a numeric weight (view=1, click=2, like=3, purchase=5). Ratings above 4 add a +2 bonus; ratings below 2 subtract 2. All weights for the same (user, product) pair are summed, then compressed with `log1p` to prevent power users from dominating the matrix.

3. **Sparse matrix construction** (`InteractionMatrixBuilder`): the strength scores are assembled into a `scipy.sparse.csr_matrix` with bidirectional index mappings (user_id to row index, product_id to column index). The matrix tracks sparsity as a diagnostic metric.

### Models

**Item-Item Collaborative Filtering** (`ItemCFRecommender`)

Computes cosine similarity on the transpose of the user-item matrix (so it measures item-item similarity based on co-interaction patterns). Optionally prunes each row to keep only the top-K most similar neighbors, zeroing out the rest. To score a user, it multiplies their interaction vector by the similarity matrix.

The model also exposes an `explain()` method that traces which specific items in the user's history contributed most to a given recommendation, returning the top 2 contributors.

**Content-Based** (`ContentBasedRecommender`)

Builds a user profile by taking the weighted average of TF-IDF vectors for all items the user interacted with. Then it computes cosine similarity between that profile vector and every product's TF-IDF vector to produce scores.

TF-IDF features are built from concatenated product fields (name, category, subcategory, brand, tags, description) using scikit-learn's `TfidfVectorizer` with configurable stop words, n-gram range, and sublinear TF scaling.

**Popularity** (`PopularityRecommender`)

Counts total interactions per product and normalizes to [0, 1]. Simple, but it handles cold-start users where the other two models have nothing to work with.

### Ranking and business rules

After the hybrid model produces raw scores, the `Ranker` applies post-processing rules before returning the final list:

- Items the user has already interacted with are excluded.
- A diversity cap limits each product category to at most 3 items in the final top-N list.
- Results are sorted by score in descending order.

### Explainability layer

Each recommendation gets a plain-text explanation generated by the `LLMExplainer`. If an OpenAI API key is configured, it sends a prompt to GPT-3.5-turbo asking for a one-sentence personalized reason. If no API key is available, it falls back to a deterministic template that varies based on whether the collaborative filtering score or the content score was dominant:

- High CF score: "Shoppers who bought items like 'X' also frequently purchased the Y."
- High content score: "Because you showed interest in 'X', we think this category is a perfect match."

### Evaluation

The evaluation script (`scripts/evaluate.py`) runs an offline backtest:

1. Sorts all interactions by timestamp.
2. Uses the first 80% as training data and the remaining 20% as ground truth.
3. Trains the hybrid model on the training split.
4. For each user in the test set, generates top-10 recommendations and checks them against what the user actually interacted with.

Metrics on the synthetic dataset (1,000 users, ~120K interactions):

| Metric | Value |
|---|---|
| Recall@10 | 0.075 |
| NDCG@10 | 0.113 |

These numbers reflect raw performance on a highly sparse synthetic dataset with uniform product descriptions. On a real catalog with richer metadata, content-based scoring would contribute more meaningfully to the hybrid blend.

## Project structure

```
src/recsys/
  config.py            Settings loaded from configs/default.yaml
  domain.py            Core dataclasses (Recommendation, ScoreBreakdown, Evidence)
  data/
    generator.py       Synthetic data generator (users, products, interactions)
    repository.py      Abstract repository + CSV implementation
    schemas.py         Pandera schemas for data validation
  preprocessing/
    processor.py       Cleaning, validation, implicit strength calculation
    matrix.py          Sparse CSR matrix builder with index mappings
  features/
    content.py         TF-IDF feature builder for product metadata
  models/
    base.py            Abstract base class for all recommenders
    popularity.py      Global popularity baseline
    item_cf.py         Item-item collaborative filtering
    content_based.py   Content-based filtering with user profiles
    hybrid.py          Strategy selection and score blending
  ranking/
    ranker.py          Post-processing, diversity caps, explanation attachment
  explain/
    llm.py             LLM-based explanation generator with local fallback

dashboard/
  app.py               Streamlit frontend
  api_client.py        Loads models and serves data to the dashboard
  components.py        HTML/CSS rendering for the UI

api/
  main.py              FastAPI endpoints for recommendations and activity

scripts/
  generate_data.py     CLI to generate synthetic behavioral data
  evaluate.py          Offline evaluation (Recall@10, NDCG@10)
  demo.py              Quick demo script for terminal output
```

## Running it

**Requirements:** Python 3.10+

```bash
# Install
pip install -e .

# Generate synthetic data (1,000 users, 200 products, 180 days of activity)
python scripts/generate_data.py

# Launch the dashboard
python -m streamlit run dashboard/app.py

# Run the evaluation
python scripts/evaluate.py

# Start the API server
python -m uvicorn api.main:app --reload
```

The dashboard auto-generates data on first launch if the `data/raw/` directory is empty.

---

## Configuration

All tunable parameters live in `configs/default.yaml`:

- `event_weights`: how much each interaction type contributes to implicit strength
- `hybrid_weights`: blending ratios for CF, content, and popularity scores
- `cold_start_threshold`: minimum interaction count before enabling collaborative filtering
- `tfidf_params`: stop words, n-gram range, minimum document frequency
- `llm_settings`: provider, model name, and timeout for the explanation layer
